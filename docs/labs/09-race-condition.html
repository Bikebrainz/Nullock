09 Business logic Hard localhost:5009

Race condition in a balance-transfer endpoint

POST /transfer reads the user's current balance, checks if it's enough, then deducts. Time-of-check vs time-of-use bug: if you fire two concurrent requests, both pass the balance check before either has deducted. Net effect: you can spend more than you have.

# then open http://localhost:5009/

Hints

Stuck? Open these one at a time -- each reveals a bit more than the last.

Hint 1

Find an action that checks a balance, then spends it, in two separate steps.

Hint 2

What happens if you fire that action twice at almost the same instant?

Hint 3

Use Intruder in a parallel/battering-ram-style burst against the transfer endpoint to win the race between check and use.

Walkthrough

  1. POST /transfer?amount=80 -- single shot, succeeds, balance now 20. (Initial balance = 100.)
  2. Reset via POST /reset.
  3. Use Intruder. Load /transfer?amount=80 as the template. Payload set: any 5 entries (the values don't matter). Set "concurrent threads" to 5.
  4. Fire. All 5 deduct succeed -- balance now -300 instead of -300. Real apps lose real money this way (BTC exchanges, gift card redemption, etc).
  5. Confirm success: GET /flag -- returns the flag once the balance has actually gone negative, which single-shot requests can never do (the check always blocks them); only the race wins it.
  6. Real fix: SELECT ... FOR UPDATE in a single transaction, or atomic decrement + check, or a queue.
